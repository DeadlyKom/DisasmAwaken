# Непрерывное удержание FD,02 и рабочие данные отсечения

[Сценарий](../Tools/Disasm/Research/CheckContinuousOverlappingKey.py)
исполняет загрузочный код исходного ACTION и 64 последовательных полётных
кадра, до входа в кадр 65. Состояние процессора и памяти между кадрами
не сбрасывается. Первый профиль удерживает FD,02 начиная с первого входа
в сканер, второй выполняется без клавиш с теми же наблюдателями.
TR-DOS обслуживается существующей подменой TraceFlight, аппаратный запуск
в Unreal этим не проверяется.

[Отчёт удержания](../Tools/Disasm/Reports/ActionContinuousKeyClipVerification.json) ·
[Контроль без клавиш](../Tools/Disasm/Reports/ActionContinuousKeyIdleControlVerification.json)

## Постоянный вход и клавиатурная рамка

После первого входа по 6F1D состояние клавиши остаётся постоянным.
Для всех чтений порта с младшим байтом FE при выборе строки с обнулённым
разрядом 1 возвращается FD, остальные строки возвращают FF. Это относится
и к многорядному опросу. До первого сканирования действует прежний
профиль портов, поэтому загрузочный код не получает искусственного нажатия.

Каждый из 64 проходов содержит ровно 27 исходных чтений по 6F34.
Для FD,02 выполняются обработчики записей 0 и 26, по 7753 и C0C9.
Их цели получены из оригинальных условий 9D4C и слов 7017, а не заданы
вместо исполнения диспетчера. Проверены действительная цель JP (HL),
слово 6F4E на вершине программной рамки, оба возврата и восстановление
исходного SP перед 6F55. Исполняются исходные обработчики и общий хвост.

| Наблюдение | Удержание FD,02 | Без клавиш |
| --- | --- | --- |
| Полные кадры | 64 | 64 |
| Входы в сканер | 64 | 64 |
| Чтения условий | 1728 | 1728 |
| Вызовы обработчиков | 128 | 0 |
| Возвраты последнего обработчика на 6F4E | 64 | 0 |
| Входы геометрических диспетчеров C070/C992 | 171 / 33 | 0 / 0 |
| Узлы вывода St13 | 9, кадры 50..58 | 0 |
| Конечный OutputSize | 34 | 0 |
| Принятые моделью IRQ | 0 | 0 |

SP сканера равен BFF8, перед выбранным обработчиком он равен BFF8-10,
при возврате на 6F4E равен BFF8-8, перед хвостом 6F55 снова BFF8.
Дополнительно прошли прежние проверки страниц и стека всех 64 полных
кадров, включая возврат кадра на A85C. Исходный SP главного цикла BFFE
не подменяется SP клавиатурной рамки.

Первый обработчик является [RequestYNegative](ActionKeyYNegative.md).
В данном профиле байт Y по 9B95 меняется с 00 на FF в кадре 4,
на FE в кадре 8 и на FD в кадре 11. Далее в проверенных кадрах он
остаётся FD. Это наблюдение за исходными накопителем, ограничителем
и хвостом затухания, значение не задаётся сценарием напрямую.

## Почему на кадре 50 меняется вход последнего обработчика

На первом входе в полёт запись A100 содержит маркер 0080 и нулевые
ModelOffset, StateCode и ClassCode. В обоих профилях кадр 8 исполняет
шаблонную ветвь [SpawnAlternate](../Source/Action/SpawnAlternate.asm).
Наблюдаются одинаковые изменения трёх физических полей:

| Писатель | Поле записи A100 | Изменение |
| --- | --- | --- |
| 78EC | ModelOffset, +06 | 00 → F4 |
| 78FC | StateCode, +0A | 00 → 09 |
| 7915 | ClassCode, +12 | 00 → 12 |

Смещения сверяются с настоящим FActionRecord из Includes. До конца
проверенных кадров других изменений значений этих трёх полей не было.
Это не утверждение о неизменности всей записи, её координаты и рабочие
поля изменяются исходным кодом.

В профиле удержания кадры 50..58 добавляют снимок именно этой записи
в очередь и доходят до RenderQueuedObject. Наблюдатель связывает
последний ReadRecord с WritePayload вставки, затем сверяет HeaderWord0
перед выводом с реальными байтами узла. Индекс исходной модели F4
становится F6 в близком варианте вывода. Оба слова исходной таблицы
9EF4 и 9EF6 указывают на E2B9 физического банка 4, авторский пакет St13.
Глубины девяти снимков равны 2205, 2219, 2236, 2219, 2218, 2180, 2130,
2093 и 2021, их старшие байты меньше исключающего порога 1F.
Имя St13 сопоставлено существующему проверенному реестру имён и файлу
[ModelSt13.asm](../Source/Action/Data/ModelSt13.asm), оно не расшифровывается
предположительно и не распространяется на все классы объектов.

Перед клавиатурным сканированием кадра 50 рабочие точки уже заполнены
нормальным рисователем в том же кадре. Последние писатели отслеживаются
во время исходных инструкций с учётом выбранного банка:

| Данные | Последний писатель перед сканированием кадра 50 |
| --- | --- |
| Первый байт FirstPoint по CF0B | C02D, ClipPolygon, узел St13 |
| Первый байт SecondPoint по CF1B | C048, ClipPolygon, тот же узел |
| CornerBlock по CF03 | C001, ClipPolygon |
| SeenFlags по CF07 | C0AC, ClipBottomToBottomLeft, значение 02 |
| OutputSize по 9BA3 | C6E6, AppendSecondClipPoint, значение 08 |

Все десять байтов обеих точек имеют аналогичную запись происхождения
в отчёте. Поэтому вход кадра 50 отличается от отдельного снимка пустого
рисователя. Сценарий не записывает точки, модели, записи объектов или
матрицу вместо игры. Сравнение двух профилей не разделяет последствия
первого клавиатурного обработчика и дополнительного входа C0C9.

## Последовательность перекрытого входа C0C9

Последний шаг всегда входит в
[ClipInsideToTopLeft](../Source/Action/ClipInsideToTopLeft.asm),
вне зависимости от того, какие ClipCode остались в общей рабочей памяти.
Обычные предусловия геометрического вызывающего при этом не обеспечиваются.

| Кадры | Наблюдавшийся путь C0C9 | Записи пары X,Y |
| --- | --- | --- |
| 1 | левое пересечение и первая отметка угла | одна пара |
| 2..49 | левое пересечение и запрос уже отмеченного угла | две пары |
| 50..55 | верхнее пересечение | одна пара |
| 56 | левое пересечение и новая отметка угла | одна пара |
| 57..64 | левое пересечение и запрос уже отмеченного угла | две пары |

В кадрах 1..49 обе точки ещё нулевые и фактический делитель равен нулю.
Это исполнение вне числового договора делителя, оно не объявляется
корректным геометрическим отсечением. После кадра 50 делители ненулевые,
но одного этого недостаточно для соблюдения согласованных зон входа C0C9.
Например, перед сканированием кадра 50 сырые точки равны
`C8 FF 76 00 96` и `4A 00 48 00 F0`, а не требуемой паре «внутри → сверху слева».

После первого вызова размер равен 2, после кадра n=2..49 равен 4*n-2.
На кадре 49 он доходит до 194. Затем нормальный рисователь записывает
свой размер, перед вызовом кадра 50 он равен 8, после вызова 10.
Поэтому нельзя продолжать прежнюю арифметическую прогрессию через кадр 50.
В конце кадра 64 размер равен 34. Все 240 записей выходных байтов,
120 обновлений размера и две отметки угла наблюдались во время настоящих
инструкций. Адрес каждого байта сопоставлен с текущим байтовым курсором.
Оборачивания курсора внутри наблюдавшихся клавиатурных вызовов не было.

## Реальное слово потока 0 перед SpawnAlternate

В обоих профилях исходный ScheduleSpawn восемь раз вызывает
[NextRandomWord0](../Source/Action/NextRandomWord0.asm) по EB72,
на кадрах 8, 16, 24, 32, 40, 48, 56 и 64. Проверяются настоящий CALL
по 7B66 и возврат на 7B69 с тем же SP. Возвращённый HL равен новому
слову физического Stream0 по EBDE. После LD A, L и реального CP
проверен Carry условного JP по 7B6C. Во всех восьми наблюдениях выбран
CheckDistance по 794B с тем же HL. Его исходный LD (799C), HL
заново проверяется после исполнения, перед загрузкой координат.

Таким образом, для этих запусков источник операнда CheckSavedWord+1
прослежен от генератора до записи без подстановки входного HL.
Слова обоих профилей одинаковы, первое равно 0DB7. На кадре 8
SpawnAlternate.Entry читает TemplateMode=0 и ThirdGate=0, затем
исполняет шаблонную ветвь. Позднейшие наблюдавшиеся входы имеют оба
байта 1. Внешний возврат равен A86A, это рамка исходного планировщика,
SP на этих входах равен BFFA.

Это дополняет отдельные составные модели
[шаблонного и случайного построителей](ActionSpawnSchedule.md).
Оно не доказывает все возможные слова Stream0, все допускающие пути
сохранённой ветви или все вызывающие контексты.

## Пределы проверки

Модель планирует прерывания существующим способом TraceFlight, однако
в этих двух запусках ни одно IRQ не принято. В наблюдавшихся вызовах
C0C9 IFF был сброшен. Это не проверка поведения при внедрённом IRQ.
TR-DOS подменён, обработчики клавиш, генератор, создание записи,
трансформация и рисователь исполняются исходными инструкциями.

После первого полётного входа не наблюдались записи банка 1 в диапазоны
C600..C9FF и DADE..DB5C, входы в временный модуль DADE..DB5C банка 1
или проверяемый фиксированный диапазон 5DA0..5EDA.
По CF08..CF0A банка 0 исполнение не наблюдалось. Высокая таблица D000
сверялась при каждом из 204 косвенных геометрических переходов.
Это наблюдения двух конечных профилей, они не доказывают глобальную
неиспользуемость байтов таблицы или отсутствие всех писателей длины
[RunTemporaryModule](ControlsTemporaryModule.md).

Произвольные клавиши, удержания свыше 128 кадров, другие сохранения,
видимые графические последствия в Unreal и авторский замысел перекрытия
не установлены. Исходная особенность сохраняется. Сборка и нативный
запуск не выполнялись.


## Оборачивание курсора при удержании 128 кадров

Тот же сценарий с `--frames 128` выполняет 128 полных последовательных
кадров и останавливается перед первой инструкцией кадра 129. Первые
64 сканирования и узлы рисования сверяются с прежним отчётом, они
полностью совпадают. Для длинного профиля ограничение стенда увеличено
с двух до четырёх миллионов инструкций, исходные CPU, RAM, обработчики
и последовательность кадров не заменяются. Прежний предел TraceFlight
по умолчанию оставлен равным двум миллионам.

Удержание даёт 3456 чтений сканера и 256 вызовов двух обработчиков.
Последние узлы рисования остаются на кадрах 50..58. После этого
геометрические входы сохраняются, скрытый вызов продолжает дописывать
по четыре байта за кадр без нового сброса размера рисователем.

| Кадр | Размер до вызова | Размер после вызова | Фактические адреса записи |
| --- | --- | --- | --- |
| 119 | FA | FE | 90FA, 90FB, 90FC, 90FD |
| 120 | FE | 02 | 90FE, 90FF, 9000, 9001 |
| 121 | 02 | 06 | 9002, 9003, 9004, 9005 |
| 128 | 1E | 22 | 901E, 901F, 9020, 9021 |

Все значения таблицы шестнадцатеричные. На кадре 120 записываются
четыре нулевых байта. По 9000 прежнее значение 49 заменяется нулём.
Курсор хранится в байте OutputSize по 9BA3 и оборачивается в пределах
9000..90FF. Это повторное использование начала буфера, выхода в
9100 в данном профиле нет. Всего скрытые вызовы выполняют 496 записей
байтов выходного буфера. После кадра 128 размер равен 34 в десятичной
записи, совпадение с итогом кадра 64 является следствием одного полного
оборота курсора за дополнительные 64 вызова.

[Отчёт удержания 128 кадров](../Tools/Disasm/Reports/ActionContinuousKeyClipVerification128.json)
содержит все записи и рамки вызовов. [Контроль без клавиши](../Tools/Disasm/Reports/ActionContinuousKeyIdleControlVerification128.json)
проходит те же 128 кадров, скрытых вызовов и оборачиваний нет, размер
остаётся нулевым. Принятых IRQ нет в обоих запусках, TR-DOS подменён.
Записи контролируемых диапазонов банка 1, входы временного модуля
и исполнение CF08..CF0A не наблюдались. Авторский замысел, все варианты
ввода и графические последствия в Unreal из этого не следуют.
